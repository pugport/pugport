# Working rules

These rules apply to contributors and AI agents. Follow the owner's explicit task scope and preserve other sessions' work.

## Runtime boundaries

- Native CLI adapters own provider protocols, sessions, and streaming; Pi owns API execution. Shared tools belong in `src/server/agent-bridge.ts` and `extensions.ts`, not separate integrations inside each adapter.
- `src/shared/bridge-catalog.ts` defines the stable external-tool discovery interface. The bridge retains direct built-in/skill tools, discovers external MCP/GitHub/connector schemas on demand, and dispatches through the original permission and audit handlers. A discovery result never grants permission; recheck current scope before execution.
- Project MCP selection is stored against the stable project ID: absent means inherit globally enabled servers, an empty list means none. Global disable and read-only constraints always apply. Do not load executable repository configuration merely because a folder is opened.
- Keep model context separate from diagnostic evidence. Preserve the actual tool name, arguments, result, and failure in the run audit, using its existing secret redaction and explicit capture limits. Add behavior tests at module or HTTP boundaries; avoid making new features depend on controller/workspace internals.
- After an initial full build/start, frontend-only changes can use `npm run build:ui`. The compatible running desktop loads the checked release when editing is safe; do not restart its backend for UI-only changes. Server, desktop, shared contracts or dependencies require a full build and a safe restart. See [Live UI updates and managed subagents](docs/live-ui-and-subagents.md).
- Collaboration is a general capability. Project conversations can delegate by default; ordinary chats stay simple until the user enables collaboration for that conversation. Internal chat work directories alone do not opt a chat in. Reuse the existing managed task graph, routing and permission checks. Real long-lived work lines are independent conversations with an explicit parent binding; do not create fake sidebar conversations for workers, bypass limits, or mark dispatch as completion. Archive/delete controls target the selected child branch, preserve the parent conversation and retain execution evidence. Native CLI-internal agents are separate unless the adapter reports them.
- Conversation jobs and peer messages use the normal task queue, routing, budgets and permission ceiling. Background wakeups cannot create more background jobs or recursive work lines. Project memory paths and fixed remote queries are explicit user configuration; do not copy private project policies into application defaults or infer authorization from a peer message. See [Project development workflows](docs/project-development-workflows.md).
- Managed child workspaces separate stable project identity from the actual execution directory. Keep Git ownership/snapshot/delivery logic in `managed-worktrees.ts`; do not bypass directory leases or treat child completion as parent integration. Project routing defaults resolve through the shared profile resolver and are captured per task. See [Managed child workspaces](docs/managed-child-workspaces.md).

## Contribution checks

- For maintainer-directed work, finish the local change, checks and build before pushing; CI on the pull request is the merge gate. Create or update GitHub issues and pull requests only when the maintainer asks for it.
- Contributors choose their own editor, model, and development tools. No skill package or AI subscription is required to report an issue or contribute. For agents working directly for the owner, use the owner's [agent workflow](docs/AGENT-WORKFLOW.md). Its pstack and Ponytail preferences are not requirements for other contributors. Tools and skills do not authorize commits, messages, publishing, or unrelated work.

- Follow the [English UI glossary](docs/ui-glossary.md) for UI copy; core terminology changes marked PROPOSED need owner approval.
- Keep one coherent task per PR. Isolate concurrent agent edits in separate worktrees and preserve others' work. Never delete through the `node_modules` or `.runtime` directory junctions.
- Claim an existing issue when starting its implementation and wait for the bot's confirmation. Reporting, discussing, and small standalone documentation fixes do not require a claim. Use `/renew` or `/unclaim` when needed. See [Contributing](.github/CONTRIBUTING.md) for the claim flow.
- Branch from current `main`. Prefer `<who>/<issue>-<slug>` when an issue exists, for example `alex/123-fix-tray`. Link the issue and use `Closes #123` only when the PR resolves it. Owner-directed local work preserves concurrent edits in an appropriate task worktree; create a GitHub issue only when synchronization is requested.
- Keep changes within the agreed task or issue scope. Report unrelated problems as separate findings.
- Run checks appropriate to the change and report anything not run. Documentation-only changes need formatting and link checks; automation-only changes also need relevant script tests and type checks. Application changes need `npm run typecheck`, `npm test`, `npm run format:check`, and `npm run i18n:check` before final acceptance, plus relevant build or desktop checks. A draft PR may arrive before these checks finish; CI still runs its configured checks. During iteration, use affected tests and run the full suite once on the final candidate unless later changes or failures require another run.
- State the exact verification commands and their actual results, the OS tested, and everything not verified. Skipped tests are not passes. Attach screenshots for UI changes.
- Label AI-made PRs `ai-made` and name the tool in the PR. Otherwise state `none`.
- Never commit secrets, credentials, personal data, private project content, or unredacted logs. Use synthetic test data. Never redeem real reset cards in tests; automatic redemption stays off unless the owner turns it on.
- Only the owner merges. The one exception is the scheduled merges by the owner's maintainer agent described in [this decision](docs/decisions/2026-11-22-scheduled-merges.md). Agents never publish or change repository settings. A label alone is not authorization.
- Request an owner decision with `needs-owner-ruling`. Record the owner's decision under [docs/decisions/](docs/decisions/README.md), then replace that label with `owner-ruled`. Respect existing decisions within their scope.
- Push authorized changes to a task branch and open a PR. Do not push directly to `main` or force-push a shared branch. Fetch the current `main` before integrating work from another machine, preserve its commits, and verify the combined result. Do not commit, push, or open a PR without task authorization.
- Tracked application source and default checks must not depend on ignored or uncommitted files. Private maintenance tools use the separate command documented in [Contributing](.github/CONTRIBUTING.md).
